# 跨平台版本控制实现方案分析报告

**日期**: 2026-06-03

---

## 1. 当前实现方案：时间戳快照 + 文件副本

### 原理

1. 用户添加文件后，系统创建文件的副本存储到快照目录
2. 每次文件修改后，根据内容变化自动或手动创建新快照
3. 快照文件命名: `{yyyyMMdd_HHmmss_SSS}_{原始文件名}`
4. 元数据存储于 SQLite 数据库（文件 ID、快照路径、SHA256 哈希、时间戳等）
5. 版本回退: 将选中快照副本覆盖回原始文件

### 技术组件

| 组件 | 技术 | 跨平台性 |
|------|------|---------|
| 框架 | Flutter / Dart | Windows, macOS, Linux, Android, iOS, Web |
| 文件操作 | dart:io | Windows, macOS, Linux, Android |
| 数据库 | sqflite (SQLite) | Windows, macOS, Linux, Android, iOS |
| 文件监听 | watcher | Windows, macOS, Linux |
| 哈希计算 | crypto (纯 Dart) | 所有平台 |
| 差异算法 | 纯 Dart LCS | 所有平台 |

### 优点

- **零外部依赖**：无需安装 Git、libgit2 等外部工具
- **真正的跨平台**：纯 Dart 实现，Flutter 支持的所有平台均可运行
- **简单透明**：快照就是普通文件副本，用户可直接访问和备份
- **轻量级**：不需要 git 仓库的 .git 目录开销，每个文件独立管理
- **易于调试**：快照目录结构清晰，问题排查直接

### 缺点

- **存储空间**：每个快照都是完整文件副本（非差分存储）
- **无分支**：不支持 Git 式的分支/合并
- **无网络同步**：纯本地方案，不支持远程协作
- **二进制文件**：大文件多次快照会消耗大量磁盘空间
- **无结构化 diff**：文本 diff 只支持行级对比

## 2. 其他可能的实现方案

### 方案 A: Git CLI 调用

通过 `Process.run('git', [...])` 调用系统安装的 Git 命令行工具。

| 特性 | 说明 |
|------|------|
| 原理 | 后台执行 git init/add/commit/log/diff 等命令 |
| 跨平台 | 依赖系统安装 Git，Windows/macOS/Linux 可安装，Android/iOS 不可用 |
| 复杂度 | 中等，需解析命令行输出 |
| 可靠性 | 依赖外部工具，不同版本差异大 |

**优点**：
- 完整 Git 功能支持（分支、合并、diff、log）
- 业界标准，生态成熟
- .git 目录标准格式，可与其他工具互通

**缺点**：
- **必须预装 Git**：Windows 用户未必安装
- **移动端不可用**：Android/iOS 无法运行 git 命令
- **进程开销**：每次操作 spawn 子进程，性能较差
- **输出解析**：不同 Git 版本输出格式可能不同
- **交互式操作**：merge conflict 等场景无法在后台自动处理

---

### 方案 B: libgit2 通过 dart:ffi

通过 Dart FFI 直接调用 libgit2 C 库。

| 特性 | 说明 |
|------|------|
| 原理 | dart:ffi 绑定 libgit2 的 C API |
| 跨平台 | 需为每个平台编译/打包 .so/.dylib/.dll |
| 复杂度 | 高，FFI 绑定复杂 |
| 可靠性 | 依赖原生库正确打包 |

**优点**：
- 高性能，无需进程通信
- 完整 Git 底层 API 支持
- 比 CLI 方案更可控

**缺点**：
- **原生库依赖地狱**：Linux 需 .so, macOS 需 .dylib, Windows 需 .dll
- **打包体积大**：每个平台需附带 libgit2 + 依赖库（OpenSSL 等）
- **动态链接问题**：实际开发中 git2dart 因 DLL 问题无法在 Windows 运行(已验证)
- **跨平台构建复杂**：CMake/iOS framework 配置差异大
- **维护成本高**：libgit2 升级时需重新编译所有平台库

---

### 方案 C: SQLite 内容存储

将文件内容直接存储在 SQLite BLOB 字段中。

| 特性 | 说明 |
|------|------|
| 原理 | 每次快照将文件内容作为 BLOB 存入数据库 |
| 跨平台 | sqflite 支持所有 Flutter 平台 |
| 复杂度 | 低，纯 SQL 操作 |
| 可靠性 | SQLite 非常稳定 |

**优点**：
- 单文件管理，一个 .db 文件包含所有数据
- SQLite 成熟稳定，ACID 事务保证
- 无需文件系统快照目录管理

**缺点**：
- **大文件性能差**：大文件的 BLOB 读写效率低
- **数据库膨胀**：频繁快照数据库文件快速增长
- **无法外部访问**：快照存在数据库中，用户不能直接查看/复制
- **并发限制**：SQLite 单写者模型
- **备份不灵活**：需导出才能获取文件副本

---

### 方案 D: 云存储同步

利用云存储 API 保存版本（如阿里云 OSS、AWS S3、七牛云）。

| 特性 | 说明 |
|------|------|
| 原理 | 每个快照上传到云存储，本地保留最近 N 个版本 |
| 跨平台 | HTTP API 可在所有平台使用 |
| 复杂度 | 中，需处理网络异常 |
| 可靠性 | 依赖网络和云服务可用性 |

**优点**：
- 多设备同步，不怕本地数据丢失
- 本地磁盘占用小
- 自动异地备份

**缺点**：
- **必须联网**：离线无法访问历史版本
- **成本**：云存储费用、API 调用费用
- **延迟**：上传下载有网络延迟
- **隐私**：文件内容存储在第三方
- **复杂度**：需处理认证、重试、冲突等

---

### 方案 E: 增量差分存储

当前方案 + 增量存储优化。

| 特性 | 说明 |
|------|------|
| 原理 | 首次保存完整副本，后续只存储变更差异(delta) |
| 跨平台 | 与当前方案相同，纯 Dart |
| 复杂度 | 高，需实现 delta 生成和 apply 算法 |
| 可靠性 | 依赖 delta 算法正确性 |

**优点**：
- 大幅节约存储空间（尤其是大文件的微小修改）
- 保持纯 Dart 跨平台优势
- 用户视角仍然是「快照」概念

**缺点**：
- 实现复杂度高（delta 生成、apply、验证）
- 恢复版本需 apply 链路（从基础版本 apply 所有增量）
- delta 链断裂会导致数据丢失
- 性能权衡：读取时需要计算，写入时快

## 4. 推荐

### 短期内（当前版本）

**保持当前方案**：时间戳快照 + 文件副本

理由：
- 软件定位是「简单版本控制」，不需要复杂分支/合并
- 纯 Dart 实现保证真正的跨平台（已验证 Windows 构建成功）
- 零外部依赖，用户无需安装任何工具
- 57 个测试全部通过，系统稳定

### 中期改进

1. **自动清理旧快照**：设置最多保留 N 个版本，超出的自动删除
2. **快照压缩**：对文本文件进行 gzip 压缩存储
3. **增量存储**（方案 E）：对大文件的微小修改进行增量保存

### 长期考虑

若未来需要 Git 兼容性，可添加 **方案 A (Git CLI)** 作为可选的后端：
- 检测系统是否安装 Git
- 若安装：使用 Git 作为版本后端（支持分支、合并等）
- 若未安装：回退到当前纯 Dart 方案

## 5. 当前跨平台兼容性验证

| 平台 | 状态 | 说明 |
|------|------|------|
| Windows | ✅ 已验证 | flutter build windows 成功，57 测试通过 |
| macOS | ⚠️ 未实测 | vscode 1.5.0 上测试通过 (集成测试) |
| Linux | ⚠️ 未实测 | 纯 Dart 实现，理论兼容 |
| Android | ❌ 不支持 | 当前以桌面端为目标，移动端需 UI 适配 |
| iOS | ❌ 不支持 | 同 Android |
| Web | ❌ 不支持 | dart:io 不可用，需改用 IndexedDB |

### 关键兼容性保障

1. **路径处理**：使用 `path` 包的跨平台 API (`p.join`, `p.basename` 等)
2. **文件分隔符**：不硬编码 `/` 或 `\`
3. **数据目录**：使用 `path_provider` 的 `getApplicationSupportDirectory`
4. **测试隔离**：测试通过 `overrideRootPath` 注入临时目录
